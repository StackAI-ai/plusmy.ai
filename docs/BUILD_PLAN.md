## Implementation changes
1. Fresh repo bootstrap: replace the current empty workspace with a clean clone of the GitHub repo, set the default branch as the base, and treat the first commit after clone as the canonical scaffold baseline for all subsequent work.
2. Repo foundation: initialize Turborepo with `apps/web` (Next.js App Router), `apps/mobile` (Expo scaffold only), `packages/ui`, `packages/config`, `packages/contracts`, `packages/supabase`, `packages/integrations`, `packages/mcp`, and `packages/core`; keep `supabase/` at the repo root for migrations, seeds, generated types, and internal Edge Functions.
3. App auth and tenancy: model `workspaces`, `workspace_members`, `workspace_invites`, and `profiles`; roles are `owner`, `admin`, `member`; all product data carries `workspace_id`, with optional `owner_user_id` for personal-scoped connections and contexts.
4. Secrets and connections: create `providers`, `provider_scopes`, `connections`, `connection_grants`, `connection_credentials`, and `connection_sync_jobs`; `connection_credentials` stores only `vault_secret_id` references for access tokens, refresh tokens, and API keys, plus expiry/version metadata; direct `SELECT` on decrypted secrets is forbidden outside internal functions.
5. Context engine: create `context_assets`, `context_asset_chunks`, `prompt_templates`, `skill_definitions`, and `context_bindings`; store embeddings in `extensions.vector(1536)` initially and expose a single `match_context_chunks(workspace_id, query_embedding, limit, filters)` RPC that applies workspace filtering before similarity ranking.
6. Audit and rate control: create append-only `audit_logs`, `tool_invocations`, and `rate_limit_buckets`; implement `consume_rate_limit(workspace_id, subject, action, window_seconds, limit)` as a Postgres RPC.
7. Integration abstraction layer: define a provider registry in `packages/integrations` where each adapter declares OAuth config, supported scopes, credential shape, refresh strategy, connection validator, sync jobs, and MCP tool/resource factories; v1 adapters are Google Drive/Docs read/search, Slack channel read/post, and Notion search/read/create page.
8. OAuth token lifecycle: resolve credentials through a server-only definer function; for an expiring token, acquire a connection-row refresh lease, reload the credential, and commit the refresh and Vault updates transactionally only while the same active, unexpired lease remains. Contention returns an error rather than an old credential. An uncertain or expired attempt fails closed and requires reconnect, since the provider may already have consumed a rotating token. Explicit reconnect atomically installs credentials and invalidates an older lease. Revoke is currently local only; provider-side revocation and secret deletion are separate work.
9. MCP server and client auth: expose `/.well-known/oauth-authorization-server`, `/.well-known/oauth-protected-resource`, `/authorize`, `/token`, `/register`, and `/mcp`; implement OAuth 2.1 authorization code + PKCE for human consent and support dynamic client registration for modern MCP clients; issue short-lived JWT access tokens with audience bound to the MCP resource server and store hashed refresh tokens in Postgres.
10. MCP tool resolution: create a per-request auth context from the MCP bearer token, map it to workspace membership and optional user scope, list only tools/resources allowed by workspace plan, connection state, and granted scopes, and inject top-k context assets into tool/resource responses via `match_context_chunks`.
11. Web product surface: ship onboarding, workspace switcher, member management, connection setup/callback pages, connection health/status, context library, prompt/skill editor, OAuth client approvals, audit log viewer, and MCP connection instructions; use the shared `packages/ui` shadcn-style primitive layer for product UI composition; keep all write paths on Node runtime routes, not Edge.
12. Mobile scaffold: create Expo auth/session wiring, workspace switcher, read-only connection status, and context browsing using shared contracts and Supabase clients; defer mobile OAuth setup flows and MCP administration UI until web is stable.
13. Background processing: keep user-facing app and MCP endpoints on Vercel; use internal Supabase Edge Functions only for queue consumers, scheduled syncs, and rate-limit/audit maintenance.

## Connection Job Fencing
- 2026-10-31 cross-provider review follow-up: when a refresh-begin RPC fails after its response may have been lost, the caller makes an ownership-matched, bounded retry to release its own unused lease before any provider call. An unused-lease release failure no longer reports success. This is best effort: a begin still executing after the cleanup, a killed process, or persistent database failures can leave a lease that later requires reconnect. Never release an uncertain lease after a provider call. Mock contracts do not replace disposable Supabase concurrency or real-provider testing.
- Dashboard job counts now recheck workspace membership and query jobs only for the actor's shared or own personal connections before applying the job limit. Query failures, an absent exact count, or a truncated connection list show an unavailable state rather than a false zero; the UI labels the 80-job recent sample. This uses multiple service-role reads, so membership changes between reads and complete pagination remain follow-up work for an actor-scoped aggregate; it does not certify a deployed privacy boundary. The connection card uses the visible connection list, and missing actors cannot match orphaned personal rows.
- Source-only migration `20260928090000_connection_write_boundary.sql` removes client DML on connections and grants and adds restrictive client policies so personal rows are visible only to their owner while credential/job references remain admin-only. Server service-role paths must continue to authorize callers; external clients that write these tables directly need a separately reviewed migration to authorized endpoints. Check actual role memberships, extra grants and policies, orphaned personal connections, migration ordering, and recovery on disposable Supabase before any separately authorized rollout. This draft changes no live grants or data.
- Release follow-ups: decide and implement the visibility/retention contract for audit and invocation payloads associated with personal or deleted connections, across direct database and service-role paths. Make the shared connection-list helper and its consuming pages surface query errors and pagination truncation instead of a possible false zero; the dashboard's connection total still uses that helper. Bind manual refresh authorization to the actor at the database boundary, review cancellation lock ordering and queued jobs entering reauthentication, and prevent a short stale-claim threshold from reclaiming a live refresh lease. Review custom non-bypass roles and migration lock timeouts against actual deployment constraints. Do not treat the connection-table policy alone as end-to-end privacy certification.
- Migration `20260928080000_fence_connection_jobs.sql` follows the frozen refresh-fencing migration without rewriting historical migrations. Each queued job records the connection's `job_generation`; every initial claim and stale reclaim receives a fresh `claim_id`, even when the same `worker_id` is reused. Cancellation clears the claim. Explicit credential install/reconnect, entry into revoked state, or a change of workspace, owner, scope, provider, or connection key changes the generation and atomically cancels older queued/processing jobs. An identity change clears any refresh lease and makes an active connection require reauthentication rather than silently losing refresh maintenance. An explicit credential install can reactivate it after writing credentials in the same transaction. Reauth-required state cannot be reactivated by sync completion.
- `schedule_connection_job_v2` requires the expected generation and an active connection. Request-level refresh passes its original generation, so an old scheduler cannot recreate a job after revoke/reconnect. Manual sync uses a separate service-only RPC that locks and rechecks the authorized workspace, generation, current membership, role, and personal ownership before queueing; it returns a conflict if fenced. Already queued work is not automatically canceled when an actor is later removed. Legacy `schedule_connection_job` (including its `enqueue_token_refresh` wrapper) and `claim_connection_sync_jobs` deliberately raise SQLSTATE `55000`; there is no compatibility fallback that guesses ownership.
- The manual sync control restores its enabled state after network errors and reports status through an accessible live region; request helper tests cover success, network failure, expected conflicts, and malformed errors. A complete browser-level race/failure test remains open.
- `install_connection_credentials_v2` installs/reconnects credentials, cancels old-generation jobs, and schedules the next refresh in a single transaction when a new or retained Vault-backed refresh reference and expiry are available. A scheduling failure rolls back the credential and job changes. The explicit opt-out remains supported; the queued-job audit is written afterward, not atomically. The old service-role install RPC still exists for compatibility and lacks this scheduling guarantee, so mixed old/new writers remain prohibited.
- `claim_connection_sync_jobs_v2`, job-scoped refresh RPCs, and `finish_connection_job` acquire the connection lock before the job lock. Claimers skip locked rows and recheck eligibility under both locks, retaining due-time ordering and the existing 900-second default stale threshold. Stale processing jobs are reclaimed directly instead of transiently becoming queued, avoiding collisions with the queued-only unique index. Attempts still increment on claim/reclaim; ordinary failures retain the existing retry limits and jittered backoff. This does not introduce singleton processing per connection/type or a new timeout/attempt-exhaustion policy for repeatedly crashed workers.
- `finish_connection_job` compares processing status, claim UUID, and generation under the same locks used by lifecycle changes. Fenced results return null with no metadata, state, or scheduling write. Accepted completion atomically applies only whitelisted sync-result fields, changes job state, and schedules a token-refresh successor from the locked connection's current expiry. If a queued same-type successor already exists, a failed processing attempt becomes canceled instead of overwriting the successor or violating uniqueness. Ordinary queued scheduling still replaces queued payload/timing as before.
- A job-triggered token refresh also checks job ownership when beginning, committing, or marking failure; the connection's existing rotating-token lease remains independently required. A committed refresh during a sync job records `refresh_schedule_pending` transactionally. The obligation survives reclaim and is fulfilled by the current owner's fenced finish even when the sync itself retries or dead-letters. A stale owner cannot fulfill it. An uncertain provider request whose job loses ownership retains its lease; it may require reconnect after expiry rather than risking reuse of a consumed rotating token.
- Completion RPC errors are outside the provider-retry catch. A lost completion acknowledgement therefore cannot requeue an already completed job or emit a fabricated success/retry audit. Audit insertion itself remains a separate best-effort transaction, not part of the atomic job outcome. Worker responses distinguish accepted `processed` outcomes from `fenced` job IDs.
